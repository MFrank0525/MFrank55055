# 全链路稳定性整改清单

## 目标

把自动上架链路拆成可逐项整改、逐项验证的稳定性清单，后续每次只攻坚一个点。

## 当前结论

本文件只保存当前稳定性门禁，不再维护会过时的“已稳定/待攻坚”状态列表。当前链路必须持续守住：飞书批次与记录身份、唯一主图 provider、类目动作隔离、店铺与水印目标身份、发布不可逆边界、断点恢复及清理闭环。实际健康状态以最新 Doctor、全量规则检查和八维深审计为准。

## 整改项

### -1. 浏览器账号态与 Cookie

风险：

- 抖店复用持久化浏览器 profile，目录里会保存登录态 Cookie。
- 主 profile 不可用时会启用 fallback profile，fallback 目录同样是敏感账号态。

最稳定方案：

1. `data/browser-profile` 和 `data/browser-profile-fallback` 必须保持 Git 忽略。
2. doctor 必须检查两个 profile 目录都没有被 Git 跟踪。
3. 不把 browser profile、cookie、storage state 复制到运行产物或提交仓库。
4. 真实发布前只使用本机已登录账号态，不在脚本里写入账号密码。

### 0. 暂停与继续

已落地：

1. 运行时默认检查暂停信号文件：
   - `data/auto-listing/control/pause.requested`
2. 如果信号文件存在，流程会在下一个步骤边界停止。
3. 停止前会写入：
   - `state.json`
   - `result.json`
   - `events.ndjson`
   - `manuals-read.json`
4. `state.json` 的 run status 会变成 `paused`，当前已经完成的步骤和产物路径会保留。
5. 暂停入口由项目控制器执行；Hermes 收到“暂停上架”时只调用 `npm run auto-listing:hermes-pause`，不直接写信号文件或杀进程。

使用方式：

1. 暂停：
   - `npm run auto-listing:pause`
2. 继续前清除暂停信号：
   - `npm run auto-listing:resume-ready`
3. 继续上架：
   - `npm run auto-listing:hermes-continue`
4. 继续时不要清理 `data/auto-listing/runs/<runId>`、真实主图工作目录、真实标题目录、店铺产物目录，否则可复用产物会丢失。

边界：

- 暂停不是强杀进程；它会等当前步骤完成后，在下一步开始前停下。
- 如果当前步骤正在调用图片接口或抖店页面，需要等该步骤返回后才会落盘暂停。
- 如果当前商品已经提交了 20 个付费生图任务，暂停不会丢弃或重复提交这些任务；项目会完成同一批 task ID 的观察和落账，并在下一个安全步骤边界停止。

### 1. 飞书卖点字段结构化

风险：

- 飞书字段可能为空或格式不满足后续提示词/标题使用。
- 卖点字段如果不结构化，会把错误带到图片提示词和标题生成。
- 飞书附件临时 URL、下载 URL 或 token 类字段如果原样落盘，会扩大账号与数据泄漏面。
- 附件下载网络抖动如果没有重试，会让整条链路在进入自动上架前随机失败。
- 多产品批次如果缺少连续性审计，可能出现飞书有 N 条产品，但本地素材或已处理清单只支撑其中一部分，导致流程中途停止。

最稳定方案：

1. 飞书产品数据读取后立即固化：
   - `brand`
   - `userCognitionName`
   - `brandedGenericName`
   - `sellingPointSegments[8]`
2. 后续模块只消费结构化字段。
3. 拆不出关键字段就立即失败。
4. 导出到 `data/feishu/products.json` 前脱敏附件临时 URL、下载 URL 和非文件级 token 字段。
5. 附件下载对瞬时网络错误和 408、429、5xx 自动重试，重试后仍失败才停止。
6. 真实运行前执行 `npm run audit:auto-listing`，审计飞书记录数、待处理数量、已处理清单和本地素材是否一致。
7. 连续性判断只放在规则层；下载、清理、项目状态输出只能作为动作层调用规则结果。
8. DeepSeek 指令和 Word 第二段使用的 `sellingPointText` 必须严格等于飞书 `产品卖点` 字段原文；不得自动追加用户认知名、品牌、产品通用名称、SPU 等结构化字段。

### 2. 图片提示词回复提取

风险：

- 可能没进入指定会话。
- 可能抓到历史内容，提取不到 5 段。
- 运行产物如果保存整页历史对话，会扩大账号信息和历史业务内容泄漏面。
- 自动重试如果不设上限，会重复消耗外部接口额度。

最稳定方案：

1. 固定使用指定会话 URL。
2. 只截取本次 prompt 之后的最后一条回复块。
3. 结果必须正好 5 段，且每段为逗号关键词。
4. 不满足就失败，不写 Word。
5. 只保存本轮回复片段、提取结果和当前视口截图，不保存整页历史对话。
6. 固定重试最多 1 次。
7. 生成请求和生成结果 URL 下载都必须有超时边界；任何一段网络调用不能无限等待。
8. 生成服务返回空数据时只能按规则重试，超过上限必须失败并保留断点，不能长时间假运行。
9. 任意图片生成请求阶段返回内容策略拦截时，都必须使用统一合规降级提示词重试；初始请求、空数据重试和 HTTP 重试分支不能各自散落不同处理规则。

### 2.1 飞书标题组合

风险：

- 标题关键词或固定后缀缺失时，无法生成合规标题。
- 把 120 个平台字符误解为 120 个汉字，会导致发布时被抖店拦截。

最稳定方案：

1. 标题可变部分只使用飞书 `标题关键词` 原词组排列组合。
2. 每条标题固定追加飞书 `标题固定后缀`，项目不再内置前缀或后缀。
3. 标题整体尽可能接近 120 个平台字符，但不得超过 120 个平台字符。
4. 平台字符按中文等非 ASCII 字符占 2、ASCII 字符占 1 计算，因此纯中文标题最多约 60 个汉字。
5. 标题保存动作必须执行同一套平台字符计数和截断保护。
6. 发布动作只能读取已审查过的标题工作簿，不允许把超长标题带到抖店发布页再等待平台拦截。
7. 标题缓存必须限定在当前产品 task 目录，禁止跨商品、跨批次复用。
8. 标题保存前必须执行飞书来源审计；不匹配时直接失败并保留断点，不能进入标题分发和发布。
9. 唯一标题不足时必须先由组合器切换起点、方向和互质步长自恢复；只有穷举仍不足才允许中断，禁止因组合算法收敛或重复而要求人工补关键词。

### 3. 中转站 image2 主图生成稳定性

风险：

- 单次接口不一定返回 4 张。
- Prompt 过重时可能直接失败。
- 即使执行时继续往下跑，缺少独立审计时也不容易快速确认每个提示词是否都达到了 4 张、类目总数是否达标。

最稳定方案：

1. 唯一有效的 provider family 是 OpenAI-compatible：模型固定为 `gpt-image-2`，模式固定为 `videos-base64`，接口精确为 `/v1/videos`；不存在其他 provider 或替代入口。白底参考图必须通过 Base64 data URL 元数据提交，并固定携带 `aspect_ratio=1:1` 与 `size=1024x1024`。配置或 Word 提示词一旦出现 3:4、2:3、竖版、横版等非方形画幅指令，必须在付费提交前 fail closed；每次请求提示词还必须重复不可覆盖的 1:1 方形画布约束。
2. 每个商品固定使用 `01-20` 共 20 个付费 slot，并以持久账本中的 slot 状态驱动恢复。`submitted` 只轮询原 task ID，`completed` 只复用结果，只有明确可重提的同一 slot 才能补交；禁止整轮或整批重放。
3. 每个 slot 的 provider task ID、provider 提交响应 `response-XX.json` 和状态响应 `response-XX-status-N.json` 均必须持久化；`request-XX.json` 也必须落盘，项目级账本还必须保存状态、响应摘要和最终结果证据。
4. 3 分钟只是操作层等待、退避和状态展示阈值，不是付费重提权限；已受理任务必须观察同一 task ID，到固定 30 分钟上限时先做最终状态查询，只有最终仍为 `queued`/`pending` 才能按同一 slot 的状态恢复。
5. 权限、余额、额度、计费、身份不明、`reserved` 或 `ambiguous` 都是付费安全阻断，不得自动重提；provider 明确证明未受理，或账本状态明确允许的有界同 slot 恢复，才可提交。`failed_before_acceptance` 且没有 `non_replayable` 证据时必须以未受理终态为准；超长 reason 被安全脱敏成 `[redacted]` 不得反向覆盖该终态并永久卡死固定 slot。
6. 不扫描、不导入旧 runtime 或历史 run 的付费账本，不提供历史迁移或其他 provider 兼容路径。
7. 实际消费文案严格来自 Word 可采纳内容，不自行增删；`audit:auto-listing` 必须审计每个提示词 4 张、类目总数达标，以及声明的主图文件和产品文件夹真实存在。

### 4. 水印与产品文件夹落盘

风险：

- 半成品提前进入正式店铺目录。
- 产品文件夹外残留图片会干扰上架。

最稳定方案：

1. 所有图片先落任务临时目录。
2. 全部批次成功后，再统一落正式店铺目录。
3. 图片移入产品图片文件夹必须使用剪切粘贴式移动。
4. 产品图片文件夹外不允许残留同批次图片。
5. 测试前先清场。

### 5. 飞书产品记录身份绑定

风险：

- 当前 task 与飞书记录身份不一致时可能串用其他商品数据。
- 空值如果放行，会把错误带到发布页。

最稳定方案：

1. 保持空值即失败。
2. 只允许使用当前锁定批次中与 task `recordId` 一致的飞书记录。
3. 导购短标题、品牌、SPU 和类目字段直接读取该记录，不读取历史商品信息 Excel，不做名称映射。
4. 飞书记录身份或字段值与发布目标不一致时直接停止。

### 6. 发布页自动化

风险：

- 页面弹窗、模板选择、履约配置、点击发布都可能波动。
- 发布成功后抖店可能跳回空白创建页，不能误判为“页面丢失”。
- 后台任务实际完成后，如果状态只看进程 PID，会误报 `exited_unknown`。
- 日志只写“开始发布”会让长流程看起来像卡住。

最稳定方案：

1. 分层测试：
   - `ready_before_publish`
   - 单产品真实发布
   - 跨店铺串行发布
2. 每个模块单独截图、单独校验。
3. 模块失败立即停止，不自动跳过。
4. 店铺切换后统一回固定标品管理 URL。
5. 直接运行发布 CLI 的真实发布类模式必须加 `--allow-publish`；默认终端只输出摘要，完整结果写入 `result.json`。
6. 发布成功判定属于规则层：必须读取 `result.json`、`state.json`、`publish-manifest.json`，不能只看后台进程是否还活着。
7. 已发布商品必须写入 `publish-manifest.json`，并以 `published + publish_signal_confirmed/list_verified` 作为安全跳过依据。
8. 发布动作属于动作层：每个商品开始、完成、失败都必须写日志；日志不改变业务规则，只为状态汇报和卡顿诊断服务。
9. 项目状态汇报必须把完成态显示为 `completed`，失败态显示为 `failed`；禁止在已有安全成功信号时显示 `exited_unknown`。
10. `填写检查`/`发布商品` 后返回空白 `/ffa/g/create` 时，只能在已尝试点击发布后作为成功提交信号；未点击发布前仍视为未填写初始页。
11. 标品管理页、发布页等后台页面短暂 loading 或浏览器上下文丢失属于可重试系统故障；规则层负责分类，动作层只能等待、刷新、重试，不能把这类故障当作已发布或直接跳过。
12. `audit:auto-listing` 必须审计已进入发布阶段的任务：每个店铺产品文件夹都必须存在安全发布信号；`failed`、`needs_manual_review`、缺失结果都视为失败。
13. 店铺切换前必须先判断当前店铺是否已经等于目标店铺。如果已经匹配，即使右上菜单仍在加载且 `切换组织/店铺` 入口暂不可用，也应视为店铺上下文满足并继续发布。
14. 当前店铺不匹配且 `切换组织/店铺` 入口不可用时，归类为可重试系统状态；动作层只能刷新、重新打开菜单、重试，不能直接把整个批次永久失败。
15. 平台明确拒绝的最终发布只允许一次跨进程持久化受控重试；子进程重启不得恢复预算。重试耗尽且完整标题列表复核仍为 0 条时，目标必须留下延期证据并从断点筛选中排除，避免同一目标无限重放拖停整批。
14.1 点击切店入口后出现“似乎出现了一些错误”平台弹窗时，必须把它归类为可恢复切店接口瞬态故障；只允许在该弹窗内唯一定位并点击“重试”，以弹窗消失或“请选择店铺”出现作为读回，最多两次。DOM fallback 必须真实执行点击，禁止只找到元素就返回成功。
14.2 店铺卡选择必须优先点击弹窗内精确店铺名称，禁止依赖构建哈希 class 或点击装饰 SVG；滚动后每轮都要重新定位精确名称，最终仍以右上角当前店铺读回为准。只有选择弹窗稳定存在且遍历后确实缺少目标名称，才允许报告目标不存在；弹窗消失并落入 loading、导航或空壳页面时属于可重试切店瞬态，必须返回规范标品页后有界重试。可见目标误报缺失时必须同时保存 DOM 与截图，便于区分“目标不存在”和“点击目标错误”。
15. 单商品恢复任务完成不等于飞书批次完成。项目状态必须同时读取飞书产品缓存和 processed manifest；只有待处理产品数为 0 时才允许显示 `completed`。
16. 已成功完成的 resume job 是过时动作文件，下一次启动前必须清理，让启动器回到正常 full-real-flow 并继续处理剩余飞书产品。
17. 项目子流程正常退出但飞书批次仍有待处理产品时，supervisor 必须自动接力启动 full-real-flow；不能只显示 `pending_products` 等人工再次启动。
18. 子流程失败时禁止自动跳过当前错误进入下一产品，必须先暴露失败原因并保留断点。
19. 项目运行中必须优先展示 state/events 里的当前 task 最新进度；上一产品留下的 publish manifest 不能覆盖当前产品的生成、标题、清理等阶段状态。
20. 多任务 run 的中间任务失败后，resume job 必须保存并复用原 `taskId`，否则会把 `tasks/image-002` 等真实断点产物错读成 `tasks/image-001`。
21. 发布创建页出现 `spu信息填充失败`、`Publish create page did not become ready`、0 个发布模块且短文本页面时，属于标品创建页预填充失败，不属于店铺错配；规则层必须归类为 `platform_spu_prefill_failed` 并允许重试。
22. 标品创建页预填充失败时，动作层不能继续修补或刷新旧创建页；必须关闭旧 `/ffa/g/create` 页面，回到标品管理重新查询 SPU 并打开新的创建页。
23. 同一飞书批次允许多个产品共享 SPU 和通用名称。发布资产匹配飞书记录时，不能只按文件夹名、SPU、通用名称做模糊反查；必须优先使用用户认知名、导购短标题、白底图/资质图文件名等强键消歧。
24. 商品详情页资质图只允许单批上传。详情图数量必须刚好等于 `从主图填入后的数量 + 飞书资质图数量`；页面计数延迟时只能等待稳定，不能再次整批上传同一批资质图。
25. 产品文件夹名如果只包含通用名称，动作层必须把文件夹内 Excel 文件名、资质图片名等可见文件名一并交给规则层判断；规则层仍无法唯一匹配时才允许失败。
26. 项目 supervisor 可能在同一日志中连续执行 resume 子流程和 full-real-flow 子流程。状态汇报选择结果文件时，规则层必须优先使用该日志中最新 run 的 `result.json`，不能固定使用启动时写入的旧 `expectedResultFile`，否则会把新批次失败误报成上一单完成。
27. 项目控制 job 里的 PID 只能作为候选信号。动作层必须读取该 PID 的真实命令并确认它仍是 `auto-listing-supervisor`；如果 PID 不存在或已被其他进程复用，状态层必须按已退出处理。
28. 同一飞书批次未完成时，任何 full-real-flow 接力都必须锁定并复用当前 `data/feishu/products.json` 缓存，禁止重新执行 `feishu:assets --cleanup-stale-assets` 覆盖旧批次素材。只有当前缓存批次 `pending=0` 后，才允许刷新飞书表格发现新批次。
29. 用户手动重新启动 full-real-flow 时也必须先审计当前缓存批次。如果当前缓存还有待处理产品，即使飞书在线表格已经更新，也必须先跑完缓存批次，不能把新批次插队到旧批次之前。
30. 同批次接力解析飞书素材时，必须先读取 `processedImageManifest` 并排除已处理记录，再校验未处理记录的白底图/资质图是否存在；已处理记录完成清理后本地素材缺失是正常状态，不能阻塞后续未处理记录。
31. 主图 raw 复用只允许发生在当前失败续跑链路的同一个 `runtimeDir/tasks/<taskId>` 内。正常重新开始、飞书新批次、历史完成商品、其他 run 的旧 raw 图片不得因为源图路径、SPU 或飞书 recordId 相同而被复制复用。
32. 抖店发布页处于 loading、基础信息所有预期字段同时消失、规格模板瞬时未读回、规格模板入口控件不可见、页面上下文丢失等发布页瞬态故障，只允许在单商品发布器内有限重试。发布阶段子流程失败后，项目 supervisor 禁止切回新的 full-real-flow 自动重放；必须保留原 run 的 manifest 和 resume 断点，由下一次项目控制器启动安全续跑并跳过已确认发布项。
33. CDP 调试端口健康探测和 Playwright `connectOverCDP` 必须设置硬超时。发布子目录持续生成的截图、结果和检查点都属于有效进度心跳，项目 watchdog 必须读取这些产物，禁止只因顶层 state/events 未更新就误杀仍在推进的发布流程。每个发布目标必须在动作开始前落盘 `not_attempted`，并在点击“发布商品”前原子更新为 `attempted_or_unknown`；发布阶段触发 watchdog 时，只有当前目标仍有明确 `not_attempted` 证据才允许 supervisor 重建 manifest-backed resume，状态文件缺失、损坏或已尝试点击都必须视为外部副作用不确定并禁止自动重启。
34. 项目 supervisor 启动的每个 detached 子流程必须登记独立进程组。子流程正常退出时清除登记；supervisor 异常退出留下孤儿子流程时，下次项目控制器启动必须终止该已登记进程组。即使进程组 leader 已退出，也必须继续清理其 npm/node 后代；只有 leader PID 仍存活且真实命令不匹配时才禁止终止，防止误杀复用 PID。
35. 规则层必须把当前 child 启动后写出的可信 terminal `result.json` 视为权威终态。成功终态且飞书当前批次仍有待处理产品时，必须立即进入同批次下一产品；禁止继续按普通运行或 stall 状态等待。terminal result 只允许保留短暂资源释放宽限期。
36. 动作层必须在 auto-listing CLI 写出终态后统一释放当前进程建立的 CDP 自动化连接。若资源句柄仍阻止 child 自然退出，项目 supervisor 必须在 terminal 宽限期后终止该已登记进程组，并按 terminal result 的真实成功/失败结果继续规则层决策。
37. 图片供应商返回 `429/502/503/504`、`temporarily unavailable`、gateway unavailable、资源过载，或主图生成阶段出现 `fetch failed`、socket reset、timeout、`UND_ERR` 等传输失败时，规则层必须归类为外部服务可用性故障。3 分钟是操作层外部服务等待、退避和慢服务阈值，不得据此重新提交付费任务。普通外部服务控制等待固定为 3 分钟且不再指数增长；已受理任务明确返回 `category=service`、`code=service_error`、`type=服务异常`，或 `upstream_error` 携带精确可用性消息 `Internet Error，请耐心等待！` / `exit` 时，固定 slot 必须进入 3 分钟起、最长 6 小时的指数熔断，禁止当前子进程立即重提。供应商 task 上的 `retryable:false` 只表示该 task 已结束，不得据此把项目永久停止。所有等待都不得被当作已受理付费任务的观察上限或无条件重提权限。必须保留当前飞书批次、当前产品断点、付费账本 task ID、原提示词/digest 和已验证 raw 图片，且不消耗普通流程有限恢复预算。`videos-base64` 已受理付费任务必须使用同一 task ID 观察，固定观察上限为 30 分钟；供应商明确成功或失败立即退出，到达 30 分钟必须执行最终状态查询，只有最终结果仍为 `queued`/`pending` 才可 stale 并只补同一固定 slot。`completed` slot 永不重新生成。内容策略、权限拒绝、access forbidden、业务校验错误和可能产生不确定外部副作用的错误禁止套用此规则。
37.1 `videos-base64` 已受理任务明确终态超时时，不得把第一个固定 slot 超时泛化成整条生图服务不可用。动作层必须在当前子进程重读持久账本并只补同一固定 slot，其他 `completed` slot 必须原样复用。只有该 slot 达到超时熔断条件时才能升级给 supervisor，并按规则层返回的精确冷却时间等待；权限、余额、计费和受理状态不明确仍必须安全阻断。
37.2 `videos-base64` 完成态结果 URL 精确返回 `HTTP 404` 时，必须先使用同一 task ID 的认证 `/content` 端点取回结果，禁止直接重提；权限、鉴权等错误继续失败关闭。若已持久化 task ID 的状态端点明确返回 `HTTP 404 task_not_found`，或任务已 `completed 100%`、结果 URL 已 404 且 `/content` 完成首次读取加 8 次同 task 退避后仍为 `502/503/504/520-524`，必须保留全部旧受理与耗尽证据，仅把该固定 slot 转为 `failed_after_acceptance` 后补交，禁止继续 supervisor 无限 3 分钟等待。累计 2 次进入固定 3 分钟熔断，其他 `completed` slot 不得变化；任务未完成、结果 URL 非 404、内容端点为权限/余额/鉴权错误或退避未耗尽时不得授权付费重提。
37.3 任意外层 HTTP 状态的嵌套供应商正文只要包含 `upstream_error`、`upstream-error`、`upstream error`、`do_request_failed` 或 `do-request-failed`，都必须进入同一固定 slot 的长退避；禁止因外层 400 或错误码分隔符差异提前终止子流程。重试耗尽且供应商明确未受理时写入 `failed_before_acceptance`，只补该 slot；已经取得 task ID 时仍只轮询该任务。
38. 任何历史运行资产恢复，包括 raw/staged 主图、异步任务响应、Word 提示词、标题、店铺商品目录、发布计划和发布清单，都必须先验证运行记录中的飞书批次指纹与当前缓存批次完全一致。指纹缺失或不一致时必须失败关闭，禁止用源图路径、recordId、SPU、产品名、文件夹名或“已有产物数量”推断为同一批次；Word 只允许从当前 `runtimeDir/tasks/<taskId>` 恢复，店铺目录只允许按 resume job 的精确文件夹清单恢复。
39. 标品查询前必须用唯一 `role=tab` 定位“平台标品”，并读回 `aria-selected=true` 后才能填写品牌/SPU或点击查询。禁止用会同时命中 tab 外层和内层节点的纯文本定位并吞掉点击错误。已确认处于平台标品后仍出现空结果时，只允许在同一店铺、同一飞书批次、同一产品身份下有限重试；耗尽后必须归类为 `spu_query_or_match_failed` 并保留截图，不能误报为未知失败。
40. Resume 状态的店铺总数必须由同一 canonical publish identity 的历史 manifest 与剩余 publish plan 合并去重得出，禁止把剩余计划长度显示成完整店铺数。医疗器械和保健食品必须保持 20 店分母；非处方药必须保持 5 店分母。
40.1 项目 supervisor 以独立进程组运行。状态检查优先验证 PID 与命令；受限环境禁止 Node 读取 `ps` 命令行时，必须用该 supervisor 的独立进程组存活信号确认运行中，不能误报任务结束并允许重复启动。
40.2 外部服务长退避期间，动作层必须写入独立 `external_service_wait` 控制状态，包含等待原因、等待次数和下次重试时间；项目状态必须优先展示该等待态。开始下一次执行时清除等待状态，禁止把正在自动等待供应商恢复误报为永久失败或正常执行中。
40.2.1 图片固定槽熔断错误已携带有效 `retry after <ms>ms` 时，supervisor 必须使用该槽位剩余期限；普通超时熔断仍固定为 3 分钟，明确 `service_error` 的持续服务故障则允许按同类失败次数增长、最长 6 小时。熔断只调整调度和状态展示，不得修改提示词、`requestDigest`、`promptDigest`、已受理任务的 30 分钟观察期限或其他付费槽位重试资格，更不得授权整批重新提交。等待状态必须优先展示剩余倒计时、准确重试时间和固定槽位，禁止继续展示终态前的旧生图进度。运行中存在当前任务但当前 runtime 尚无发布清单时，必须优先展示当前任务状态，禁止读取同一 supervisor 日志中上一商品的发布模块。
41. 项目实时进度必须由项目状态命令输出统一的 `realtimeProgress` 信号，并通过 Hermes 面向外层的 `hermesProgress.key/message` 暴露，包含 supervisor 启动时间、active runId、当前商品组进度、当前店铺组进度、当前发布 runtimeKey、最新进度时间和来源。外层自动回复器必须记录完整 `hermesProgress.key` 作为心跳，并按 `hermesProgress.message` 级别的稳定 key 去重播报；禁止继续用旧 `expectedResultFile`、旧 `state.currentTask`、历史发布计数、原始 `publishProgress.safelyPublished/total` 累计数、`last_safely_published` 或跨 run 残留的本地 watcher key 推断是否有新进度，也禁止因为 key 中时间戳/产物心跳变化每分钟重复播同一模块。当前 active run 已写入 terminal failed result 时，项目状态必须优先展示终态失败/外部等待信号，禁止再用 terminal 之后异步图片任务追加的 events 误报为正常实时进度。续跑重新进入较早水印时，状态聚合必须以当前 active 发布项的更新时间作为当前尝试窗口，忽略更早的后续水印失败残留；禁止旧 `needs_manual_review` 记录把当前进度误报成后续水印、20/20 店铺或历史失败项。
41.1 Hermes 进度中的完成数和当前位置必须分开表述：飞书 processed manifest 是“批次已完成 X/Y”，当前 record 序号是“当前第 A/Y”；当前商品安全 manifest 是“发布已完成 N/20”，下一个/正在执行项是“当前目标 M/20”和“当前店铺 S/T”。跨商品 manifest 只能按 canonical `batchFingerprint + recordId + taskId` 分组，禁止按展示名或通用名合并，也禁止把跨商品累计安全条目截断成当前商品 20/20。停止或失败时，当前任务 recordId 与发布清单 recordId 不一致必须隐藏旧发布清单，展示当前商品的主图/前置阶段；暂停结果即使晚于 manifest 写入，只有同一 recordId 的 `published` 任务才能保留当前商品发布断点，不得退回已完成的主图 20/20。Hermes 心跳 key 必须包含 recordId，商品名优先使用飞书用户认知名；暂停/停止通知必须直接播报项目 `hermesProgress.message`，不得回退到已隐藏的累计字段并显示 `0/?`。
41.2 Hermes 的主动反馈必须绑定触发 `开始/继续/查询上架` 的精确平台、聊天、话题线程和消息 ID；消息 ID 必须读取 `MessageEvent.message_id`，禁止从不拥有该字段的 `SessionSource` 读取。项目版本化的 durable router plugin 必须独立持久化同一 origin，以跨 gateway 重启和 Hermes 包升级恢复；每条主动反馈必须通过 `reply_to` 直接回复该触发消息。origin 或回复消息 ID 缺失时必须失败关闭并保留待发送状态，禁止发送无锚点消息、遍历 channel directory、读取 home channel 或猜测历史线程。飞书发送只有同时取得成功响应和非空 `message_id` 才算送达；发送失败或缺少回执时不得推进 notice 去重状态，下一轮必须继续重试。已受理生图 task 长时间保持同一队列状态时，watchdog 仍必须读取项目最新 `hermesProgress` 心跳，并至少每 10 分钟发送一次带回执的存活通知；禁止因为 service-wait key 未变化而永久沉默。
41.3 Hermes 收到精确的开始、继续、暂停或状态自然语言控制后，durable router plugin 必须在 `pre_gateway_dispatch` 中完全接管并返回 `skip`，立即结束普通会话/模型分发。开始和继续必须先回复已接收，再在事件循环后台调用项目控制器；禁止只改写为 slash command 后同步等待控制器，避免控制器预检超过网关超时后被前端显示为 Hermes“思考”。真实插件加载、hook 注册、即时回复和后台 action 必须由可执行集成测试验证，禁止只靠源码正则或文件存在性宣称生效。
42. 主图生成完成是标题、店铺分发、发布和清理前的硬门禁。每个当前商品必须先通过主图完整性审计：总数等于类目计划、每个 Word prompt 的图片数等于计划、raw 无水印文件、staged 水印文件和商品目录均真实存在，并且 raw 与水印图的真实像素宽高必须相等。供应商返回非方图时必须保留原图证据、按长边白底居中等比补成正方形并在补边后重新加店铺水印；禁止重复提交已完成付费 slot、拉伸或裁剪商品。新下载、同 task 复用、店铺目录恢复和发布前续跑必须共用同一尺寸动作。任何缺失、重复、数量不足、文件不存在、尺寸无法读取或非1:1都必须 fail closed，禁止继续进入标题、分发或抖店发布。
42.1 真实店铺访问审计与上架发布必须互斥。审计入口在任何浏览器动作前读取 `auto-listing-child.json` 并校验 PID；只要真实上架子进程仍存活，就必须 fail closed，先请求安全边界暂停。禁止审计与发布共享同一抖店浏览器上下文并发运行。
43. 生图前允许做抖店登录预检以避免未登录后浪费图片费用，但项目状态命令对 Hermes 展示的进度必须明确标注为 `login preflight`。登录预检不是发布动作，禁止在状态文案里把它描述成发布进度；真正发布只能在主图、标题、资质、店铺分发全部完成并通过门禁后发生。
44. `videos-base64` 的单商品 20 张并发提交是允许的，但仅限首次提交当前商品当前批次的 20 个异步 task。同一商品只要已有 task ID、轮询状态、部分 raw 图片或暂存图，任何 `fetch failed`、abort 或网络中断都必须进入外部服务等待并续查同一批 task；已受理任务必须观察同一 task ID 直至明确终态或 30 分钟最终查询后仍为 `queued/pending`。禁止 supervisor 快速重启生成新的 runtimeDir 后再次提交 20 个付费任务，也禁止重新生成任何 `completed` slot。
45. 付费图片账本属于当前未完成产品的项目级恢复控制状态，固定保存在 `data/auto-listing/paid-image-submissions`，不得放在 runtime task 目录。项目 controller/supervisor、清理和续跑都必须尊重该共享账本；Hermes 不读取、不修改账本。产品安全完成后删除产品账本，批次完成或确认重跑时删除整批账本，禁止把共享账本长期保存为历史主图库。
45.1 任何发生在 `published` 阶段的主图尺寸失败或发布前主图完成门禁失败都必须留在 manifest-backed `resume` 路径，禁止 supervisor 回退到 `full-real-flow`。当前批次付费图片账本仍存在时，完整流程的 stale-run 清理和共享店铺/标题/主图目录预清理必须关闭；未完成商品的运行目录、发布清单和店铺资产不得被当成下一商品的陈旧输出删除。
45.2 已知续跑起点的发布恢复只加载当前商品尚未安全完成的精确目标集合，例如第18店失败时必须包含第18至20店并排除已有安全证据的第1至17店。发布前尺寸门禁必须对该剩余子集逐个验证 product folder、raw、水印图、唯一性和真实正方形尺寸；不得把3个剩余目标误当成“重新生成不足20张”，也不得因子集门禁放松单文件完整性。只有完整20目标安全清单覆盖后才能标记产品完成、归档、清理或推进下一飞书产品。
45.3 发布断点完成最后一组目标后，归档输入必须合并状态 artifact 与当前 task 目录中全部合法 `openai-compatible/raw/generated-*` 文件，并按绝对路径去重；不得因 artifact 只描述剩余3个目标而忽略磁盘上已完成的前17张。`cleaned` 阶段归档门禁失败必须重建 cleanup resume，禁止回退到 `full-real-flow` 或重新发布。
45.4 深度审计不得把“剩余目标 resume artifact”误当成完整生图 artifact。当前商品尚未完成且 state 只记录剩余发布子集时，审计只能用精确 `recordId` 匹配全部店铺商品目录，并与当前 `runtimeDir/tasks/<taskId>` 中按 prompt/slot 编号的 raw 文件一一重建完整证据；必须同时满足 20 个唯一目录、20 张 raw、5 轮各 4 张和真实文件存在。任何缺失、重复、跨 record 或模糊名称匹配都必须保留原失败，不得用付费账本数量掩盖磁盘资产缺失。
46. 20 个 slot 和 5 个提示词轮次必须使用 all-settled 协调。任一 worker 失败时必须等待其他 worker 落账后再退出；`reserved` 或 `ambiguous` 是安全阻断，项目 supervisor 禁止自动重启或再次提交。
47. 详情资质图必须逐张通过商品详情专属 input 上传，并以每张上传后的预览计数 `+1` 作为确认；禁止回退到其他图文模块的通用 file input。首个商品目录在既有图文模块重试后仍出现确定性资质上传失败时，必须停止该商品剩余目录，禁止重复跑完全部水印。只有 manifest 证明失败发生在最终提交前且不存在 `submit_accepted_unconfirmed` 等不确定副作用时，supervisor 才允许重建 resume 任务；已安全发布项必须跳过。
48. 飞书资质图在上传抖店前必须解码检查像素尺寸；任一边超过 `5000px` 时，在当前发布 runtime 内生成最长边 `4900px`、等比例缩放的合规副本并复检。合规原图不得放大，飞书缓存和商品目录原图不得覆盖；探测、缩放或复检失败必须在浏览器上传前失败关闭，禁止回退上传超限原图。
49. 项目运行中，控制器、状态、doctor、审计和业务子流程调用的 `npm run build` 必须是覆盖式安全编译，不得删除正在被其他 Node 进程加载的 `dist`。删除旧编译产物只能通过 `npm run build:clean` 在控制器已停止的离线交付阶段执行；禁止把 clean build 嵌入任何运行中状态查询或恢复动作。
50. 规格模板唯一真值是当前飞书记录的 `规格模板` 字段。动作层只能选择与该字段去除首尾/显示空白后完全一致的下拉项，不接受别名、包含匹配、类目默认值或标题推断。下拉中没有完全一致项时，当前目标保持 `not_checked`，立即停止批次并让 Hermes 仅汇报“没有对应的规格模板可选”。最终提交前失败统一为安全未提交，终态错误使用最后实际阻塞项。项目状态一旦进入 `failed/completed/stopped`，终态消息必须压过旧 `hermesProgress` 心跳；Hermes watcher 必须先投递并按状态加失败摘要去重，不能依赖已从 Hermes 载荷隐藏的发布累计计数。共享 runtime 的 manifest 可保留同批次其他 task 的合法目标，身份审计必须按当前 task 计划限定比较作用域；尚未执行的目标只能记为待执行身份，不得误报为身份损坏，重复/越界身份仍必须失败关闭。
51. 店铺真实商品规格 DOM 只出现 `添加规格类型（0/3）`、`规格预览` 而不存在 `规格模板` 时，属于店铺配置缺失，不得按页面瞬态无限重试，也不得跳过该店铺继续上架。项目禁止重新引入手工创建规格值动作；必须在最终提交前以 `not_checked` 安全失败停止当前批次，通过 Hermes 明确汇报需要用户在该店铺配置受控规格模板。用户配置完成后，只能从同一批次、同一目标的安全断点续跑。
52. 抖店登录态由平台服务端和风控策略控制，项目不得承诺“一次登录永久有效”，也不得自动输入账号、密码、验证码或扫码凭据。项目必须固定使用专用浏览器 profile，禁止清理或轮换该 profile 来规避登录失效；启动前、店铺切换前和最终提交前必须做只读登录态预检。检测到 `doudian_login_required` 时属于外部人工阻塞，不得重启发布子流程、不消耗普通恢复预算、不继续后续店铺；当前目标以 `not_checked` 安全停止。项目 supervisor 必须保持 `doudian_login_wait` 可观测状态并保留 manifest 精确断点，只允许周期性执行只读登录预检；Hermes 必须明确提示用户在固定有头浏览器登录。只有预检确认同一 profile 会话恢复后，才能自动从原断点续跑。
52.2 固定抖店浏览器 profile 必须由跨进程原子租约保护。发布、登录复检、店铺审计和诊断动作在任何 CDP 连接前都必须取得同一租约；存活 owner 存在时第二个进程必须 fail closed，禁止共享 profile、关闭对方页面或重启对方浏览器。owner 进程结束后允许回收 stale lease，非 owner 禁止释放。店铺切换看到登录页时必须在规范 SPU 页面上做有界二次确认，避免一次瞬态重定向中断批次；确认登录失效后仍按 52 条等待人工恢复，禁止尝试绕过平台认证。
52.1 CDP 端口可被同机其他浏览器项目占用；连接前必须同时验证调试端口和项目专用 `user-data-dir`，禁止只因 `/json/version` 返回 Chrome 就接入。其他 profile 占用的端口只能跳过，禁止连接或关闭；项目必须保留独立备用端口。真实只读巡检必须写满 20 店并收敛为终态，半途报告不得视为通过。
53. 商品管理列表的逐店完整标题预查默认关闭。只有发布顺序已经紊乱且无法定位续跑店铺时，才允许显式使用 `productListPreflightMode=unresolved_disorder`；正常批次以及已明确从哪个店铺续跑时必须使用默认 `known_sequence`，按 manifest 和精确断点直接执行，不得逐店查询。某个店铺已尝试最终提交但结果不确定时，只允许对该店铺做定点核验，不得触发后续店铺的批量预查。凡执行完整标题核验，都必须锁定唯一商品状态 Tab 组，等待异步 DOM 就绪，并读回“全部”选中态；禁止在角色 Tab 尚未出现时退回全页面同名文本，因为商品类型、草稿审核、好评率、商品分组等筛选器也会显示“全部”。查询提交后必须等待 URL 中完整标题、结果总数、加载结束和“结果行或明确空状态”同时成立。固定延时、页面级标题回显、未稳定表格或未知遮罩都不能证明商品不存在；无法闭环时必须停止、保存失败截图并禁止重提。
54. 最终点击发布后，若抖店在发布页明确返回同时包含“系统异常”以及“请重试/稍后重试/操作ID”的错误条，则属于平台明确拒绝本次提交，不得因同页的“必填项进度”等无关文本误分类为普通表单校验，也不得直接盲重提。动作层必须先对同一店铺、同一 canonical target、同一完整标题执行“全部”Tab 的稳定只读核验：找到商品则记为 `list_verified`；明确为 0 条才允许清除未完成表单断点并完整重建发布页做一次受控重试。第二次仍被明确拒绝或列表核验无法闭环时继续失败关闭，禁止后续店铺和再次提交。
55. 商品发布页已进入 `商品规格`，但真实 DOM 缺少 `规格模板` 栏并报 `Spec template field root was not found` 时，属于抖店生成了异常发布页，不代表店铺未配置模板，也不得误报为价格库存失败。当前页禁止刷新和继续填写；恢复必须关闭异常 `/ffa/g/create` 页，回到标品管理页重新输入当前品牌和 SPU，从结果行重新点击发布商品，完整重建同一 canonical target。最多执行三次受控重建；全程尚未触发最终发布，不需要商品列表查重，重试耗尽后安全停止且不得跳过当前店铺。
56. 非处方药平台标品身份必须包含飞书完整 `规格`。同一品牌文本对应多个抖店品牌身份时，冻结精确同名的 `standard_brand_id` 顺序并逐个查询；同一 SPU 对应多条规格时，只允许选择规格标准化后与飞书值精确一致且唯一可发布的行。不得按 DOM 顺序、评分或模糊包含关系选择；品牌候选耗尽仍无匹配时安全停止。
57. 平台标品候选读取与“发布商品”点击必须共享同一个 DOM 身份。候选采集只接受可见叶子数据行、直接 `td` 单元格和唯一可见可操作控件，并在同一次采集中为控件写入临时身份；规则层选中的候选只能通过该身份交给 Playwright 点击。禁止在规则层选中后重新扫描全部 `tr`，也不得把平台隐藏表格副本、嵌套表格父行或粘性列镜像计为第二个业务结果。
58. 最终提交后的普通校验错误只允许来自当前可见错误提示组件，禁止扫描整个页面正文并把商品状态说明、“需在已下架操作上架”或“必填项进度”常驻文案当成平台拒绝。没有成功信号且没有可见错误时必须保持最终提交不确定。只有独立审核动作取得相隔至少十分钟的两次稳定完整标题 `共0条` 证据，并精确校验 result、manifest、canonical identity 和店铺路径后，才可把唯一清单项迁移为 `pending + not_checked + reviewed_negative_retry_approved`；审计只计为进行中，一次受控重试后不得再次授权。
59. 店铺切换前若出现“平台已为您开通优质快递服务-平台智能透标模式”已知信息弹层，动作层必须在该精确文案范围内定位唯一关闭控件，使用 DOM locator 点击并读回弹层消失后再打开右上店铺菜单。禁止把遮罩导致的“切换组织/店铺”不可见误报为店铺能力缺失，也禁止通过坐标点击、模糊关闭未知弹层或点击“查看详情”绕过。

## 推荐执行顺序

1. 先稳生成侧：
   - 飞书卖点字段结构化
   - 图片提示词回复提取
   - 中转站 image2 出图
2. 再稳文件侧：
   - 水印落盘
   - 产品文件夹归档
   - 商品信息匹配
3. 最后稳发布侧：
   - `ready_before_publish`
   - 单产品真实发布
   - 跨店铺串行发布

## 执行原则

1. 每次只攻坚一个环节。
2. 已稳定步骤不重复改动。
3. 未触发步骤不提前联动。
4. 当前点失败，就先修当前点。
5. 禁止只为当前失败点写临时补丁；必须先分析根因，再做可复用的长期修复。
6. 每个修复必须明确归属：
   - 规则层：业务判断、成功/失败条件、恢复/跳过条件。
   - 动作层：浏览器点击、输入、上传、读取页面、截图。
   - 状态层：checkpoint、manifest、resume job、运行记录。
   - 数据层：飞书字段、标题表格、图片/资质文件。
7. 优化结果必须把动作和规则分开保存，避免后续排查时分不清是规则变了还是动作坏了。
