# 2026-08-10 不确定提交的审核后负向证据恢复

## 生产证据

- 当前批次：`3891df866b4e4781b1ec7816`，非处方药 20 个发布目标。
- 卡点：第 2/5 店第 8 个目标，`北方经开锁阳固精丸-recvrMGe4Yg7i3-水印08`。
- 发布按钮点击已进入持久化不可逆边界，但页面没有出现成功信号，初次“全部”页完整标题查询稳定返回 `共0条`。
- 2026-08-10 再次在同一目标店用同一完整标题做只读查询，仍稳定返回 `共0条`；两次证据相隔超过 7 小时，商品没有延迟落库。
- 普通继续命令正确拒绝重放，但项目缺少把“人工复核后的双重稳定负向证据”转为一次性恢复授权的动作，因此整批永久停在 7/20。

## 根因

状态机只有两条不确定提交出路：完整标题查询找到商品则记为 `list_verified`；查询未找到则永久保留不可逆边界并打开熔断。这个默认行为保证安全，但没有独立的人工审核恢复通道，导致已经由长时间间隔的双重负向证据证明“未创建商品”后仍无法继续。

另一个清理缺口是完整标题核验动作创建独立持久浏览器后没有在 `finally` 中关闭 context，独立核验命令会留下进程。

## 根治

1. 普通 continue 仍不得重放任何不确定提交。
2. 新增独立 `auto-listing:recover-uncertain` 人工审核动作；它不发布商品，只生成一次性恢复授权。
3. 恢复动作必须同时验证：持久化状态是 attempted-but-unconfirmed、精确标题与店铺身份一致、边界已超过十分钟、已有一次稳定 `not-found` 截图、实时再次查询仍为 `共0条`。
4. 动作先归档原始 result 和复核证据，再写入绑定精确标题与店铺路径的批准标记。任意正向或不确定查询均拒绝批准。
5. 正常继续流程只有在批准标记身份吻合且再次实时查询仍为 0 时，才允许完整重建一次；第二次再出现不确定结果仍立即停止，不能再次恢复。
6. 完整标题核验浏览器在成功和失败路径均关闭 context。
7. 发布结果识别只允许从当前可见错误提示组件提取普通表单阻塞；页面常驻的“需在已下架操作上架”“必填项进度”等帮助文案不得升级为提交拒绝。平台系统异常仍按“系统异常 + 请重试/稍后重试/操作ID”的组合信号单独识别。
8. 审核动作在批准标记落盘后，必须用相同 canonical identity、runtime key、店铺路径和 result 路径精确匹配发布清单，并把该唯一条目迁移为 `pending + not_checked + reviewed_negative_retry_approved`。原不确定结果和两轮负向证据继续归档。审计只把此状态计为“进行中”，不得计为已发布；任一身份不一致都必须失败关闭。

## 安全边界

恢复动作是显式人工复核动作，不属于自动重试。普通恢复、崩溃恢复和同批继续都不会自行创建批准标记。批准标记不能跨标题、店铺或目标复用。
