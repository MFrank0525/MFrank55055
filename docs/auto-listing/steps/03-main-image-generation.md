# 步骤 03：生图与水印

## 目标

按飞书字段 `产品类目` 读取对应数量的 Word 文档，通过唯一有效的 OpenAI-compatible `videos-base64` provider 生成主图，并为后续本地水印、无水印归档与产品文件夹整理准备原始图片。

- 医疗器械：5 轮，每轮 4 张，总计 20 张主图；按店铺顺序每 1 张打一个店铺水印，分发到 20 个店铺。
- 非处方药：5 轮，每轮 4 张，总计 20 张主图；按店铺顺序每 4 张打同一店铺水印，只分发到前 5 个店铺。
- 保健食品：5 轮，每轮 4 张，总计 20 张主图；按店铺顺序每 1 张打一个店铺水印，分发到 20 个店铺。

## 动作脚本

- [main-image-assets.ts](src/autolist/main-image-assets.ts)（历史文件名，实际节点为主图生成）
- [local-watermark.ts](src/autolist/local-watermark.ts)
- [local-watermark.py](src/autolist/local-watermark.py)

## 输入

- 5 份 Word 文档
- OpenAI-compatible provider 的 API Key
- 固定模型 `gpt-image-2` 和固定接口 `/v1/videos`
- 当前飞书白底图；适用固定图框时，程序在本地生成一张包含白底商品与真实品牌框占位的单一布局参考图，再以 Base64 data URL 发送

## 输出

- 每轮实际送给生图模型的 `image2-prompt.txt`
- 每个固定 slot 的 `request-XX.json`、提交响应 `response-XX.json` 和状态响应 `response-XX-status-N.json`
- 持久付费账本中的 provider task ID、状态、响应摘要和最终图片结果

## 操作说明

### 飞书主图提示词来源规则

主图提示词只有一个组装入口和三个层次，固定生成契约是唯一权威来源，禁止在其他模块追加同义规则：

1. 固定层：项目版本化维护的产品保真、文案边界、高级感与转化目标，只出现一次。
2. 商品层：飞书 `主图主标题`、`主图副标题`、`主图卖点` 选出的已审核产品文案，以及当前轮本地千问产品场景。
3. 轮次层：当前本地千问需求场景、每轮四种构图、20 套艺术字、图框安全区、1:1 方图和单海报约束。轮次层不得用固定视觉类型覆盖需求场景。

每份 Word 文档只保存两段变量：

```text
第一段：已固化的完整产品文案
第二段：当前轮新生成的本地千问产品场景
```

飞书不再需要 `主图指令`、`正向提示词`、`反向提示词` 三列；即使历史表格仍保留或填写这些列，程序也不得读取或发送。项目不维护“违禁词清单”或通用反向词列表，因为新增海报文字只能来自已审核产品文案。`image2-prompt.txt` 必须按固定层、商品层、轮次层顺序组装，每条规则只出现一次。

### 单图构图与禁止拼图硬门禁

1. 每个付费 slot 是一次独立请求，只允许返回一张连续、完整、单场景的商品海报。5 轮 × 每轮 4 张表示 20 次独立图片结果，绝不表示把 4 张图排在一张画布中。
2. 提示词必须明确禁止四宫格、九宫格、2×2 网格、4 合 1、拼图、分屏、分栏、多面板、联系表、前后对比拼接，以及四个象限重复展示商品。
3. 每张新下载 raw 图在方形补边、图框、水印和店铺分发前必须通过本地单图结构检测。检测到中心横纵分隔且多个象限均为有效画面的四宫格/多面板结构时，立即保存 `.collage-rejected.json` 证据并失败关闭；禁止靠裁切、缩放或加框掩盖。
4. 单个固定槽位命中四宫格/多面板时，必须归档原 provider task、原图和检测证据，只把该槽位从 `completed` 安全迁移为 `failed_after_acceptance`；其他已完成槽位禁止重提。相同提示词和单海报强约束下每个槽位最多接受 3 个 provider 输出，前两个不合格时仅重生该槽位，第 3 个仍不合格则停止付费重试并明确告警。
5. 当前失败任务恢复 raw、店铺产物恢复和发布前续跑必须重新执行同一门禁，不能因为图片已经生成、已加水印或已进入断点而绕过。恢复扫描只允许识别 raw 目录直属的 `generated-NN.png/jpg/jpeg/webp` 原图；`.unframed`、`.frame-ready`、检测证据、provenance 和其他派生文件都不得成为恢复输入，也不得在每次续跑继续派生。
6. 门禁版本和单图提示词契约必须进入业务规则指纹；规则变化后旧断点不得静默沿用。

### 固定图框规则

1. `宝元堂`、`久光小泽`品牌不使用固定图框；其余品牌默认必须使用清洁图框 `assets/auto-listing/default-main-image-frame-v2.png`。
2. 中转站每次仍只能提交一张参考图。图框品牌必须先把当前产品白底图与真实固定品牌框合成为一张 `full-bleed-visible-frame-guide-v4` 布局参考图，不得拆成两张无空间关系的参考图，也不得退回只靠文字描述安全区。
3. 图框商品的完整提示词只追加一次固定品牌区约束：左上角横向 `0%–68%`、纵向 `0%–20%` 是参考图中品牌框及其右侧、下方呼吸区；该区域只允许连续的低细节背景与自然光影通过，所有文字、商品、人物、图标、色块边缘和高对比装饰不得进入、重叠或相切。长主标题任何笔画的顶边必须位于纵向 `23%` 以下，主标题与副标题组成的信息组整体只能放在纵向 `24%–42%`。参考图中的品牌框不得放大、延长、复制或仿制。
4. 模型返回后，程序必须保留未贴框原图用于测图和复核。程序不得为了避让品牌条缩放、裁切、移动或非线性变形供应商海报；`frame-ready` 必须与原尺寸供应商海报逐像素一致，然后只把项目固定图框逐像素覆盖到原尺寸画布。
5. 店铺水印不得污染固定图框的不透明像素。
6. 最终图框成图固定为原图框 800×800 尺寸；原图框完全不透明像素必须与固定资产逐像素一致。
7. 图框文件摘要只参与本地后处理证据，不得进入中转站参考图数组或 provider 身份。
8. 后续新增不套图框品牌，只能修改集中例外名单并补充规则测试。
9. `.unframed.png` 是供应商原始成图，`.frame-ready.png` 是原尺寸、未重排的贴框前证据；两者必须逐像素一致，并与最终贴框图同时保留到测图验收完成。缺失未贴框原图的旧贴框产物不得自动二次贴框或进入新流程。

### 视觉差异化与质量门禁

1. 五轮分别执行本地千问给出的五个用户需求场景。人物、手部、使用部位、纯商品、步骤、原理、配色、光线和道具均由当前需求决定，不得按固定“临床/生活/科技/纯商品/方法”模板强加。
2. 每轮四张分别采用左产品、右产品、中央英雄和近景/俯视构图；构图只负责同场景差异化，不得改变用户需求、消费时刻和环境语义。
3. 20 个固定槽位分别绑定 `文字系统01` 至 `文字系统20`，不得复用。每套文字系统同时约束主标题艺术字、副标题异形承载图形、卖点专属图标和排列方式；禁止退化为默认黑体、纯文字列表、统一盾牌或统一对勾，也禁止只换颜色而复用同一字形和图案模板。
3.1 每个已验证 `locationConcept` 必须绑定自己的背景主导配色；包装原色不参与背景色裁决。海滩、高山、城市街道、车内、公园露营等不同地点不得因为包装暖金色而统一生成暖金、米黄或橙棕大面积背景、底栏或标题牌。
4. 步骤图、人物或纯商品展示都不是必选项。需要说明使用方式时才加入步骤，需要生活代入时才加入人物，需要突出选择理由时才使用纯商品或证据细节；任何表现手段都不能压过用户需求或虚构商品事实。
5. 商品必须完整、清晰、可识别，并与场景建立直接关系；商品、人物和环境的相对大小按需求决定，不使用固定面积比例硬套。
6. 20 张全部落地后、店铺产品目录创建前，必须先执行传统视觉质量门禁：精确数量、正方形、近重复、暖金过量和轮次配色同质化。
7. 传统门禁通过后，必须由本机 Ollama `qwen3-vl:8b` 逐张读取最终成图和对应本地千问场景，检查用户需求、主要环境、商品完整可见、左上品牌框以及呼吸区。呼吸区必须把标题、商品、人物、图标、色块边缘和高对比装饰全部挡在左上 `68%×20%` 之外，并确认标题从纵向 `23%` 以下开始。视觉模型必须从同一受控地点枚举返回画面主地点，程序再硬校验“成图地点＝目标 `locationConcept`”且五个目标场景不复用类别。视觉模型只能连接 HTTP loopback，不得调用外部网页或远程模型；任一图片的需求或环境不匹配、地点错位、商品不清楚、品牌框被遮挡或呼吸区不足时，整组失败关闭并保留 `main-image-scene-adherence-report.json`。
8. 暖金主导图片最多占 40%；超过 8/20、出现近重复、轮次配色几乎一致或本地视觉场景门禁失败时，整组不得创建正式店铺产品目录或进入发布。

### 内容策略拒绝后的飞书源修订

中转站明确返回内容策略或安全策略拒绝时，禁止使用“内容策略兼容降级提示词”或任何程序自创的中性提示词。程序只能从当前飞书记录的 `主图主标题`、`主图副标题`、`主图卖点` 候选中换用一个未使用组合，并保持步骤 01 的产品文案结构。任一候选变化都必须重新调用本地千问，重新生成 5 个产品场景和 5 份两段式 Word；旧本地千问场景、旧 Word 和旧请求摘要全部失效。新产品文案与旧本地千问场景、旧产品文案与新本地千问场景的任何混用都必须失败关闭。

## 执行要求

1. 每轮只处理一份 Word 文档，Word 份数由产品类目决定。
2. 生图模型实际消费的变量内容只能取两段式 Word：已固化的完整产品文案与当前轮新生成的本地千问产品场景；固定契约只能由单一组装函数追加一次。
3. 产品卖点必须以候选词填入固定结构后固化的完整单段文本进入 Word 第一段，固定文字、顺序和标点不得删改。
4. 文案内容必须严格按照 Word 文档中的可采纳内容执行，不允许自行添加，也不允许自行减少。
5. 水印内容必须严格只按上面的 20 个名称和顺序执行，不允许自行添加、减少、改名或调换顺序。
6. 每轮任务都必须单独记录真实提交文案。
7. 生图 provider 明确返回失败状态时，立刻失败，不继续等待。
8. 正式生图前先执行一次 provider 配置预检；若 API Key、模型、接口地址缺失，立刻停止，不进入生图提交。
9. 任何失败都不允许提前写正式店铺目录。
10. 当前 Mac 飞书真实流程唯一有效的 provider family 是 OpenAI-compatible：模型固定为 `gpt-image-2`，模式固定为 `videos-base64`，接口必须精确为 `/v1/videos`。请求必须通过 Base64 data URL 元数据把当前飞书白底图作为输入参考图传给模型；主图生成尺寸固定为 `1024x1024` 正方形；每轮固定 4 张图，轮数由产品类目决定。不存在其他 provider、同步模式或兼容入口。
11. 如果 provider 返回余额、额度、计费不足等错误，必须明确提示充值中转站账号。
12. 充值或解除 API Key 独立额度上限后不得直接编辑付费账本。只有专用充值恢复动作可以解除固定槽位：控制器必须已停止，原槽位必须是带 `non_replayable` 的 `failed_before_acceptance`、明确 HTTP 403 `insufficient_user_quota/用户额度不足/pre_consume_token_quota_failed`、没有 provider task ID 和响应摘要；动作先归档产品身份与原槽位账本，再追加人工批准审计并仅授权相同槽位重新提交。其他权限、计费、受理不明或已受理任务继续失败关闭。
12. 如果当前产品在同一个 `runtimeDir/tasks/<taskId>` 内曾在生图或后续步骤中断，已成功生成并保存的 raw 图片必须优先复用，只补缺失图片，不允许无必要重复消耗额度重新生成。
12.1 raw 主图复用边界只限当前失败续跑链路。正常重新开始上架、飞书新批次、历史完成商品、其他 `data/auto-listing/runs/<runId>` 里的旧 raw 图片一律不能复用；即使产品、SPU、源图路径或飞书 recordId 看起来相同，也必须以当前飞书表格批次为准重新走生图流程。
13. 如果前面的步骤已经完成且没有问题，修复问题后必须从当前出错步骤继续，不重复执行已完成步骤。
14. OpenAI-compatible `videos-base64` provider 不得再读取历史三列或拼接额外正反向词；只执行统一组装后的最终提示词。
15. OpenAI-compatible `videos-base64` provider 必须按类目执行：医疗器械、保健食品和非处方药均为 `5 个 Word × 每个 4 张`。只有当前失败续跑 task 目录内已生成且未使用的问题外节点产物可以继续复用，不重复生成；其他历史 run 产物不得参与当前批次。
16. 固定生成契约只负责产品保真、文案来源边界和视觉质量目标，不包含可持续膨胀的违禁词或反向词清单。
17. 产品包装以白底参考图为唯一事实来源；海报新增文字只允许来自飞书已审核的主标题、副标题和卖点，程序不得创造其他商品事实。
18. 同一份 Word 生成 4 张图片时，由项目轮次层分别指定左产品、右产品、中央英雄和近景/俯视构图，本地千问 不承担同轮四图差异化。
19. OpenAI-compatible provider 每次都必须发送当前飞书源修订绑定的统一完整提示词。接口明确返回 `content_policy_violation`、`policy_violation`、`safety`、`moderation` 或等价中文内容策略拦截时，必须从当前飞书记录的 `主图主标题`、`主图副标题`、`主图卖点` 候选中重新选取组合，并重新生成本地千问场景与 Word 后补同一失败 slot；禁止自动重试平台兼容、中性或简化提示词。
20. 每次源修订必须持久化新旧产品文案摘要、修订 ID 和本地千问来源摘要；中转站请求前必须读回 Word 第一段精确等于当前产品文案、第二段精确等于当前修订的新本地千问场景。新旧本地千问或产品文案混用立即失败。
21. OpenAI-compatible provider 遇到 `429/500/502/503/504` 时视为中转站临时故障，必须自动退避重试并写入 `response-XX-transient-N.json`；普通 `429/500` 临时 HTTP 故障最多短退避 3 次。若返回内容包含 `system_memory_overloaded`、`memory overloaded`、`resource overloaded`、`server overloaded`、`do_request_failed`、`do-request-failed`、`upstream_error`、`upstream-error`、`upstream error`，或状态码为 `502/503/504` 网关侧不可用，必须执行 8 次长退避重试（60s、90s、120s、180s、180s、180s、180s、180s），即使外层 HTTP 状态为 400 也不能因为嵌套上游错误而直接停止整批上架。外层 `HTTP 400` 若正文是带 `400 Bad Request` 标题和 `openresty`/`nginx` 标记的代理 HTML，也属于中转站反向代理瞬断，必须使用同一套 8 次长退避；只有业务 JSON 参数校验类 400 才保持失败关闭。遇到 `fetch failed`、网络断开、socket reset、timeout、`UND_ERR_*` 等传输层瞬断时，也必须自动退避重试至少 8 次，并写入 `response-XX-transport-transient-N.json`。流程重跑时如果当前轮已经有水印暂存图，只补齐缺失数量，不重复消费额度重生已暂存图片。

33. `videos-base64` 提交等待时间必须与普通下载/状态查询超时分离，默认至少覆盖该供应商的完整异步轮询窗口。供应商已经受理但提交响应较慢时，项目必须继续等待任务 ID，不能因为普通 180 秒请求超时提前制造 `ambiguous` 槽位。
33.1 `videos-base64` 付费提交请求收到 `429/5xx/520-524` 时不得直接重发同一付费 POST；必须持久化原始响应并进入 `ambiguous` 安全阻断。只有响应正文自身明确满足 no-acceptance 合约，或第 34 条的供应商 token 日志严格证明零扣费、无上游请求且与该固定 slot 唯一一一对应时，才允许只重试该 slot。状态查询和结果下载的退避策略不得复用于付费提交。
34. 无法自动找回任务 ID 且已有受理/扣费风险的 `ambiguous` 槽位永久禁止因时间经过而自动重新提交。只有通过项目自有的显式对账恢复动作，验证供应商任务 ID 和状态、确认任务未失败并写入审计原因后，才能把该槽位恢复为 `submitted`；恢复后只允许轮询同一个任务 ID。任何续跑在启动并发提示词 worker 前必须先完成已有 `ambiguous` 的只读对账，禁止一边对账一边提交其他可重试 slot。若 ambiguous 槽位没有 task ID、没有供应商响应摘要，且原因属于提交阶段传输失败，项目可自动写入 no-acceptance 审计并转为 `failed_before_acceptance` 后重试同一固定 slot。对于持久化的不明确供应商可用性响应，仅支持 `502/503/504/520-524`：Cloudflare 页面必须提取出标题状态码与 `Error code` 完全一致；结构化 JSON 必须是有界嵌套的 `fail_to_fetch_task`，最内层精确为 `system_unavailable`、`category=system`、内外两层 `retryable=true`，并包含合法唯一 `client_request_...` ID。这两类响应都只允许进入只读对账，绝不直接授权重提。供应商 token 日志还必须同时满足错误类型、同一模型、`quota=0`、没有 `upstream_request_id`、正文中的 `status_code` 与 `error code` 相等并精确等于本地状态码，而且与全部待对账槽位在 5 秒时间戳窗口内形成数量相等的一对一完美匹配。日志接口是最终一致的，首次查询未形成完整集合时只允许每 5 秒刷新一次只读日志、最多 37 次（总刷新等待不超过 3 分钟）；刷新期间不得修改账本或发送任何付费 POST，只有某次查询取得完整集合后才能统一写入审计。全部条件成立后，项目才可统一写入响应摘要哈希和日志 ID 的 no-acceptance 审计，并且只重试这些固定 slot；5 秒时间戳窗口用于覆盖日志整秒精度，与 3 分钟只读可见性刷新上限相互独立。同秒并发的多个槽位和多个日志允许按集合一对一匹配，因为集合内每条日志都独立证明零扣费、未受理；日志多出、缺少、状态码不一致、状态码不在白名单或无法形成完美匹配时必须拒绝，且不得部分放行。任一条件缺失或日志查询失败都必须维持安全阻塞。操作员仍可在中转站后台明确证明未受理、无任务 ID 且未扣费后，通过显式无任务对账恢复其他槽位。若旧版本把“供应商任务明确失败”误记为 `ambiguous`，只能通过项目自有的显式 provider-failure 对账动作，把同一 task ID 的槽位转为 `failed_after_acceptance` 后再允许只补该固定 slot。
34.1 同一子进程完成首次严格未受理对账后，只允许立即补交对应固定 slot 一次。若这次补交再次形成 Cloudflare 网关 `ambiguous`，必须在全部并发请求 settled 且 `reserved=0` 后再次执行第 34 条完整日志对账；证明完整时先把槽位安全迁回可重放的 `failed_before_acceptance`，写入仅由项目内部产生的精确 `provider_log_no_acceptance_reconciled` 标记，再以 `retry after 180000ms` 交给 supervisor 进入 3 分钟外部服务冷却，禁止在当前子进程立即第三次提交。安全分类器只对该内部精确标记解除原始 submit 文本的歧义判定；普通供应商正文或自然语言“未受理”不得获得同等授权。第二次证据仍不完整则继续安全阻断。不得因为“当前子进程只补交一次”的边界而跳过最终对账、遗留本可证明未受理的 `ambiguous` 并要求人工续命。
34.2 Cloudflare 网关 `ambiguous` 无法形成第 34 条零扣费证明时，必须额外检查同一模型、`type=2`、`quota>0`、`is_task=true`、`request_path=/v1/videos`、请求 ID 与上游请求 ID 均存在的精确计费日志。匹配前必须先用账本内每个“已有 `providerTaskId` 且存在 `submitted` 审计”的槽位提交时间，在 5 秒窗口内对已知计费日志做数量相等的一对一完美匹配并排除；排除范围包括 `submitted`、`completed` 和 `failed_after_acceptance`，不能只排除完成态。任何已知任务槽位无法唯一归属时必须整体拒绝，不得把它的计费日志错归给未知槽位。排除后，只有剩余计费日志在本地网关响应持久化后的 5 分钟内出现，并且与全部待对账槽位形成数量相等的一对一完美匹配时，才可标记 `provider_log_billed_acceptance_without_task_id`；同秒并发且候选窗口重叠时按集合匹配，不要求每个槽位只有一个局部候选。每次只读日志刷新都必须同时尝试零扣费与已扣费严格匹配，不得先傻等完整零扣费窗口再检查已扣费证据。该标记只证明任务已受理和扣费，永远不得授权重新提交；状态输出必须明确要求从供应商任务日志找回公开 `task_...` ID，再通过项目正式对账命令验证任务状态和创建时间、写回账本并只轮询该任务。零条、多余、缺少、字段不全、非 `/v1/videos` 或无法形成完美匹配时仍保持普通安全阻塞。
34.3 显式任务 ID 对账校验供应商任务创建时间时，必须以该槽位最后一次持久化提交响应的 `updatedAt` 为时间锚点，不得使用批量预留时的 `createdAt`。串行提交会让后置槽位在预留后等待数分钟，使用预留时间会把真实任务误判成不属于该槽位；时间窗口仍必须有界，且任务 ID、状态和模型校验保持不变。
34.4 五个提示词轮次可以并发准备请求，已受理任务可以并发生成、轮询和下载；只有付费 POST 接单窗口必须 single-flight。第一笔不明确响应在准入锁内立即熔断，保证一次供应商故障最多新增一个 `ambiguous`，其余排队 slot 未发出 POST、未扣费且可安全续跑。仅在第 34 条或 34.5 完成严格对账后才能复位熔断器。
34.5 token 日志严格证明任务已扣费但响应丢失 task ID 时，项目必须使用独立持久化浏览器配置打开供应商任务页；未登录时保留可见登录页并持续等待，不得退出或重发。登录后只读查询任务列表：查询窗口可围绕计费时间前后各 15 分钟以覆盖 `submit_time` 与 `created_at` 的服务端排队差，但最终归属必须按 `created_at`/计费日志 5 秒窗口、完整槽位集合一一匹配；任务行未暴露私有模型字段时不能据此拒绝，若明确暴露且模型不一致则必须拒绝。每个候选 task ID 还必须通过 API 的 ID、非失败状态和十分钟提交窗口验证后，才可写回原 `ambiguous` slot 并只轮询原任务。任何数量、时间、状态或一一对应关系不完整都必须整体失败关闭。
34.6 供应商 token 日志查询本身出现 `fetch failed`、连接重置、超时、HTTP 429 或 5xx，只代表只读证据源暂时不可用，不得解除 `ambiguous` 安全阻塞，也不得立刻把 supervisor 终止为人工阻塞。动作层必须在第 34 条既有 37 次/3 分钟窗口内继续只读刷新，期间不得修改账本或发送任何付费 POST。若整个窗口一次成功日志响应都未取得，必须写入精确 `provider_log_lookup_unavailable` 标记；supervisor 保留当前批次、产品、固定 slot 和全部已完成图片，进入统一 3 分钟外部服务等待，且不消耗普通恢复预算。等待结束后只能重新执行 ambiguous 对账前置检查；只有严格零扣费证据才能授权补交，严格已扣费证据只能进入原任务找回，其他情况继续安全阻塞。
34.7 任何收到 HTTP 响应但无法取得任务 ID 的付费提交，必须在进入 `ambiguous` 的同一账本事务前将完整原始响应按 SHA-256 固化到产品级 `evidence/`，并把相对路径、摘要、HTTP 状态和采集时间绑定到该 slot。后续恢复只能读取并校验这份产品级证据，不能按当前恢复 runtime 猜测响应文件。历史账本若尚无该字段，只允许用 slot 已持久化的精确 `owner.runId/taskId` 定位原 runtime，验证 Cloudflare 页面后迁移一次；迁移完成后同样只读产品级证据。
34.8 已接单日志排除必须枚举每个 slot 审计中全部 `submitted` 事件，不能只读当前 `providerTaskId`；后续固定 slot 重试会替换当前任务字段，但历史扣费仍会出现在供应商日志中。同一 slot 的多次接单必须作为独立尝试参加全量一对一匹配。供应商扣费时间为整秒且早于本地收到响应，已验证最大差值 7.136 秒，因此历史接单排除使用 10 秒窗口、模糊网关扣费识别允许响应前 5 秒；两者都必须保持完整集合基数严格相等，出现额外或缺失日志仍失败关闭。
34.9 token 日志长期缺失时不得无限空转。若当前产品恰有一个 `ambiguous` 槽位，必须用独立已登录浏览器只读查询该槽位最后一次预留前 60 秒到网关响应后 5 分钟的供应商任务列表。只有响应明确为第 1 页、返回数等于 `total`、返回数小于 `page_size`，窗口内全部已有 task ID 与账本已知集合完全相等，并且恰好多出一个非失败任务时，才可把这个唯一任务归属给唯一 ambiguous slot。随后仍必须通过任务 API 再验证 task ID、模型、创建时间和非失败状态，写入 `submitted` 审计后只轮询该 task ID。分页不完整、已知任务缺少、多于一个未知任务、未知任务失败、时间越界或模型冲突时必须继续阻断。供应商证据等待的 supervisor 后续循环必须使用精确 `resume`，不得用 `full` 刷新锁定的飞书批次。
35. 断点恢复必须按固定文件槽位识别已有和缺失图片，禁止按已有文件数量推算下一槽位。例如当前轮存在 `generated-02/03/04` 且缺少 `generated-01` 时，只能恢复或补齐第 1 张，不能重复复用第 4 张凑数量；staged 文件必须与同槽位 raw 原图一一对应。`videos-base64` 每轮续跑进入 provider 前必须输出固定缺失 slot、真正付费提交 slot、复用 slot 和轮询 slot；真正提交数量必须等于当前账本中 missing、`failed_before_acceptance` 或 `failed_after_acceptance` 的固定 slot 数，禁止因本地 raw/staged 缺失而重新提交已完成账本 slot。
36. 续跑控制器在进入发布前必须重新验证每个已存在主图轮次的固定 raw 槽位完整性。任一轮次缺少 `generated-01..04` 中的任何槽位时，即使旧状态已记录为发布阶段，也必须强制回到 `main_images_generated` 修复并验证，禁止信任旧的“主图完成”标记直接发布。
37. 主图尺寸校验必须覆盖新下载 raw、当前 task 断点复用 raw、staged 水印图、店铺产品目录水印图和发布前恢复路径。发布前即使只从精确店铺目录恢复，也必须重建 raw 与产品目录的一一映射，修复历史非方图并重新加当前店铺水印，再执行主图完成审计。审计必须读取真实像素宽高；只检查数量、路径或文件存在不构成主图完成。
38. `videos-base64` 付费提交前必须验证参考图字节数。原图超过供应商单图 6MB 上限时，项目必须在当前 runtime raw 目录生成最长边不超过 2048 像素、严格小于 5.5MB 的已完整解码 JPEG 参考副本，并记录尺寸、字节数和质量证据；飞书原图不得被覆盖。由该确定性预处理引起的 request digest 变化只允许迁移明确 `failed_before_acceptance` 的相同 slot，且 prompt digest 必须保持不变；`submitted`、`completed`、`failed_after_acceptance` 或 `ambiguous` 均不得借此换图重提。供应商错误正文、嵌套 JSON 和并发聚合错误必须在进入日志或 Error 对象前移除回显的 Base64 请求体并有界截断，禁止超大错误掩盖真实错误码或再次触发 `Invalid string length`。

## 失败条件

- 生图 provider 提交失败
- 生图 provider 余额不足、额度不足、API Key 无效或账户不可用
- provider 状态响应明确返回失败终态
- 生图完成但无图片文件
- Word 文档读取失败

## 人工检查点

1. 核对 `image2-prompt.txt` 是否按固定契约、产品变量、轮次变量和输出约束各一次组装。
2. 核对 Word 只有产品文案与当前轮产品场景两段，且最终提示词不含 `主图指令`、`正向提示词`、`反向提示词` 历史字段内容。
3. 核对 `request-XX.json` 是否显示 `mode=videos-base64`、模型 `gpt-image-2`、接口 `/v1/videos`，且 Base64 参考图元数据包含当前飞书白底图、`metadata.aspect_ratio=1:1` 和 `metadata.size=1024x1024`。
4. 核对 `response-XX.json`、`response-XX-status-N.json` 与持久付费账本是否保存同一个 provider task ID、最新状态和响应证据。
5. 确认只把当前产品已审核文案、当前轮场景和项目单一固定契约送给生图模型。
6. 确认水印内容顺序严格为：大药房专营店、药品专营店、个护保健专营店、康复理疗专营店、医疗保健专营店、理疗器械旗舰店、健康护理专营店、家庭护理专营店、中医保健专营店、养生器械专营店。
